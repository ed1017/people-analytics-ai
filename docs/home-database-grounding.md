# Home conversation evidence grounding

The ordinary Home route verifies loaded evidence before constructing the model client. It invokes the existing allowlisted aggregate GET readers locally, under the same request-pinned dataset context, and compares the normalized supplied facts, observation dates, canonical scopes, population labels, source metadata and selected detail/monthly rows. A selected row can be outside the default three-row sample; it must still occur in the current source, with multiplicity preserved. The dashboard's verified filter receipt must match the requested filters. A changed or unavailable loaded source returns 503 before provider dispatch; a stale dataset header returns 409 before the handler runs. Earlier work remains intact and the user must refresh explicitly.

The exact accepted packet remains unchanged, preserving existing proposal/review/save bindings. Server-derived model context includes the dataset token, normalized packet SHA-256, retrieval time, per-source observation date, reader path and source classification. `read_evidence` returns the same provenance. The legacy token `legacy-v1:0` identifies the active routing context, not an immutable certified import. Separate source reads are not one transactional database snapshot. Different source dates remain different; an unknown date is not replaced with retrieval time or September 30.

Only already loaded source groups are reread. Missing sources stay null and unavailable; they are not zero or evidence of absence. Database aggregates, stored scenarios, the separate public BLS reader and fictional/unverified session inputs are explicitly distinguished. Frameworks supply general method only. Owner responsibilities are suggestions, not proof that an actual company role or person exists. All supported staffing/workload/cost arithmetic remains in existing calculators; user/model assumptions remain provisional, visible and correctable. The existing bounded source-scope contradiction check also guards final prose.

This changes no SQL, relation, permission, credential, dataset selector, model policy, tool/round ceiling, retry policy, calculator, saved-plan schema or explicit Choose/Apply boundary. Existing reader implementations continue to own access and suppression; some existing handlers aggregate employee-level records internally. This change consumes their allowlisted aggregate outputs only and adds no raw-record model/tool export. BLS retains its existing separate public-source request. Grounding has two reader workers and an eight-second total response deadline raced against the entire verification. A read failure, unavailable result, caller abort or timeout aborts the shared signal and stops scheduling. Timeout returns unavailable before model dispatch even if an in-flight reader ignores cancellation. Dashboard and attrition forward the signal to their existing Supabase fetches; BLS forwards it to fetch. Other existing readers may continue internally, and fetch cancellation is not proof that PostgreSQL stopped work already received. The two-reader limit is per grounding operation, not a global database query limit. Every loaded source must finish and match before model use; there is no subset fallback, new cache or retry.

The live legacy route previously normalized the browser packet without server revalidation. Projection inputs already used fresh reads; the candidate dataset's separate certified provider already has its own rebuild contract. This verifier deliberately accepts only the current legacy provider. It does not select, certify or cut over to the prepared 9,847 dataset.

Offline tests use fictional aggregate responses with the real verifier, request wrapper, service and POST. They cover stale dataset headers, tampered values/dates/rows, duplicate row use, filter mismatch, unavailable sources, missing role readiness, source-date separation, suppression, framework-vs-company namespaces and unsupported scoped assertions. Browser replay uses the real verifier with synthetic aggregate input. These tests are not live database attestation, real-model recommendation acceptance or independent forecast validation. General free-text claims still need semantic review: neither a valid citation nor successful arithmetic proves a causal explanation, feasibility, actual availability or future benefit.

## Existing reader authorization assumptions

At the reviewed source, no root/src middleware or proxy file exists and `next.config.ts` has no route authentication configuration. Each allowlisted GET handler was inspected for cookie, session, Authorization/header identity and user-scope dependencies. The handlers expose existing app aggregates using the server Supabase client; none of the fourteen handlers implements per-user authentication or row ownership. This is evidence about repository code, not a proof of deployment-level authorization or user-scoped equivalence.

| Handler(s) | Existing request-dependent checks retained by direct invocation |
|---|---|
| dashboard | country/org/level query, verified RPC filter receipt; existing performance-release filter and digest checks |
| career-growth-mobility | method and query validation; aggregate output only |
| succession-coverage | method, URL, no-body/header validation; existing suppression contract |
| workforce, attrition, talent-acquisition, survey-sentiment, skills, learning-development, career-mobility, workforce-planning, position-modeling, finance | existing company aggregate handlers, no user identity or additional filter context |
| bls | separate fixed public BLS request, no company/user identity |

The thirteen workforce readers retain their `withDatasetRequest` wrapper, inheriting the pinned context and checking the explicit dataset header; BLS remains separate. Direct invocation does not traverse HTTP middleware, deployment protection, WAF or edge rate limiting. The outer Home HTTP request remains subject to its normal deployment path, but no infrastructure configuration was fetched or modified in this local preparation. These readers must not be described as user-authorized datasets. If a future reader requires identity or middleware-provided context, it must be excluded/fail closed until that context is explicitly supported; missing authorization cannot be repaired by a new grant or fabricated header.

When all company sources are unavailable, no database read is invented: conditional qualitative advice can proceed with null evidence. I3/D1 remain fictional or unverified session inputs, never database actuals. Stored scenarios remain conditional modeled records, not current observations. No zero-hallucination guarantee is made for unrestricted prose.
