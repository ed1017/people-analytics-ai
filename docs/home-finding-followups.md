# Home finding follow-ups

Home's existing structured response may designate at most four findings with `id`, `text`, `evidence`, and `prompt`. This is an output-only addition to the existing request and evidence boundary. No extra generation call, source fetch, person-level data, or planning calculation is introduced.

Each ID is unique within the answer (`f1`–`f4`). Text is at most 280 characters and must equal the complete plain-text body of one unique `- ` bullet, including its citations and relevant limitations. Prompts are unique, single-line questions of at most 240 characters. One to three unique references must be present in the existing available Home evidence catalog. The text's cited source set must match those references. Invalid, missing, unavailable, ambiguous, or oversized metadata yields no controls while preserving the answer. This checks structural correspondence and availability; it does not prove that a model's free-text interpretation is semantically correct.

`Explore this finding` appears only beside a designated bullet, with its follow-up question visible. An occupied composer disables Explore and explains that the user must send or clear the draft first. A synchronous guard also rechecks the actual draft before sending. Clearing the composer never sends automatically. Explicit activation with an empty composer sends that finding and question through the existing Home chat envelope, retaining pinned goal context and any new draft typed while the request is pending. A successful explanatory follow-up does not display an options-preparation warning merely because it proposes no options. App-owned instructions preserve scope, sampled coverage and uncertainty, and forbid inferred causes, individual risk, retention effects, automatic changes or calculation. The ordinary answer, links, candidate options, and planning controls remain intact.

Action metadata lives only in the current page session, separate from stored chat text and model transport history. The binding includes exact assistant-message identity, goal, evidence context, source snapshot and request epoch. Activation consumes it synchronously to prevent duplicate sends. A new request, goal/context change, explicit evidence refresh, or page exit invalidates it. Restored answers and reference-history views cannot reactivate actions; refreshing evidence does not replay a question.

Validation covers schema and production route decoding with an isolated model stub, malformed pairs and unavailable evidence, exact correspondence and bounds, plus built-app intercepted-network checks for draft preservation, keyboard activation, duplicates, stale changes, reload, and desktop/mobile/200% reflow. No live model request or hosted Attach mutation is part of this slice.

## Response completion and diagnostics

Home checks response completion before decoding JSON. Incomplete output caused by `max_output_tokens` returns `token_limit`; other incomplete responses, refusals, empty output, and completed-but-invalid JSON have separate fixed reasons. Partial output never becomes an answer or an Explore control, and validation does not retry or salvage partial JSON. These failures return a fixed error plus `homeReplyDiagnostic`, containing only allowlisted status/reason values, the configured output ceiling, byte count, and numeric token usage (including reasoning tokens when supplied). Model prose, provider errors, request content, credentials, and refusal text are never included in these diagnostics or logged by this handler.

Ordinary Home generation has a 4,000-token ceiling and explicitly detailed generation has 6,000; these include reasoning and structured metadata. The visible answer targets remain 80–120 and 250–300 words respectively. These are ceilings rather than usage claims. The previous generic `invalid_json` failure did not establish whether output was truncated; a new hosted check must inspect the safe completion diagnostic before attributing a cause. The normal single-request path is retained, and another attempt requires an explicit Send.
