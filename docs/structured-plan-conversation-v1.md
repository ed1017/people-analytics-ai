# Goal-aware Home conversation and read-only tools

The current slice supersedes the earlier one-turn saved-plan command protocol and its twelve-call acceptance proposal. It is disabled by default. Build an isolated preview with `NEXT_PUBLIC_HOME_SOLUTION_CONVERSATION=true` to use the new flow. The old `NEXT_PUBLIC_HOME_STRUCTURED_PLANS` protocol remains for compatibility; the new flow takes precedence and has no mode checkbox. No hosted flag, model, database routing or production setting is changed by this PR.

## One conversation

Ordinary questions and app work use the same Home composer. A time question can call the read-only server clock, render it in the browser's supplied IANA time zone, and answer directly without a goal or proposal card. A later deadline request can resolve the actual discussed plan and display a reviewable change. There is no phrase classifier or special command syntax in this path. This is not a general web or live-facts integration.

Context includes the actual current goal, normalized scoped Home evidence with facts/dates/limitations, goal notes, current saved IDs and revisions, selected plan when present, recent turns, current interpreted constraints, working candidates, rejected ideas and unresolved questions. Current evidence and plan snapshots supersede historical claims. The browser decision store is the plan authority; server validation is not authentication or an independent workforce-data attestation.

The configured `CHAT_MODEL` is unchanged. The Responses API can choose bounded read/calculation tools: `read_clock`, `read_evidence`, `read_plans`, `evaluate_candidate`, and `project_headcount`. Tool errors and calculator feedback are returned to the model for correction or explanation. A turn permits at most four provider rounds, six tool calls, 5,000 output tokens per round, 120,000 UTF-8 bytes of accumulated input, 30 seconds per provider request and 90 seconds overall. The final round disables tools. There are no automatic retries, model switches or write tools. The endpoint accepts at most 900 KB before validated context construction.

A response can discuss the problem, ask a focused question, propose a fresh approach, or adapt any useful combination of actual saved/working activities. There is no required fixed menu, count or pair selection. Proposals include rationale, tradeoffs, next step, success-measure approach, exact lineage and visible input interpretations. Intervention mechanisms remain hypotheses; evidence of a problem does not prove an intervention effect.

## Typed assumptions and review

Quantities use normalized values, units, exact references or relative expressions. Code resolves values from saved/working revisions and applies scale factors. For example, a 0.5 factor on the referenced participant count halves that actual number. A same-people link shares group identity rather than counting the same people twice. A user-turn reference records provenance; it does not prove the model interpreted the user correctly. The review exposes those interpretations.

Retained activities preserve valid unaffected inputs and provenance. Added, adapted or removed activities invalidate affected costs, timing, population mappings, aggregate effort and outcome scenarios. Shared cost coverage and cross-source population/cost overlap remain unknown until reviewed. Participant membership changes clear overlap certainty unless a single shared group remains. Current corrected constraints take precedence; typed removal records a user-turn tombstone so an older statement cannot restore a withdrawn cap. Removed constraints clear inherited corresponding assumptions; known cash/hour/horizon violations block Save. Coupled staffing redesign remains discussion-only pending the existing staffing calculation. Supported currency is USD; unsupported units are explained rather than silently converted.

Unknown population or horizon does not prevent useful discussion or a qualitative saved proposal. `reviewBundleProposal` returns an explicit `awaiting-scope` review with all aggregate results unknown. The existing `reconcileBundle` calculator still rejects missing scope. A qualitative alternative can be attached to its goal with an explicit `proposal-selection` association. Operational Apply and legacy execution attachment still require calculated scope. Reload preserves that distinction. No placeholder population, date, duration, cost or impact is invented to pass a gate.

Unpinned exploration, its transcript and working proposals persist in a separate browser workspace before a goal exists. The intended flow is **“I want to reduce turnover” → proposed Action Plans → intentionally Choose a plan → automatically pin “Reduce turnover” with that proposal attached → refine through conversation**. The desired outcome is a separate field from an intervention objective such as “Run a mentoring trial”. There is no mandatory Pin Goal step before proposals. Browsing details or discussing a plan does not select it. The button says “Choose plan, pin goal and attach proposal”; selection publishes the goal, transcript, working state, immutable numbered plan and proposal association in one checked storage transaction. Unknowns require acknowledgment. Repeat selection is idempotent; existing goals, plans and attachments are preserved. Fictional first-run examples do not reserve a user goal title and remain untouched. Duplicate user goal statements stop selection with the exploration retained rather than overwrite an existing goal. A failed storage write leaves no orphan pinned goal. All source dependencies, including quantity-only expressions and inherited working dependencies, enter lineage and are checked again before selection. Goal/scope/evidence changes, cancellation, stale responses and explicit retry are checked in the UI and core contracts.

## Explicit release acceptance requirements

The user's requirements are release criteria, not optional polish: ordinary context-carrying conversation; grounded but fluid, useful and creative Action Plans beyond preset choices or dashboard rows; chat-driven headcount projections; and intentional plan selection that automatically pins the desired goal and attaches the proposal. Novel mechanisms and unproven effects must be labeled honestly. Evidence limits facts and calculations, not the range of ideas the assistant may explore. Neither fixture passes nor a successful deployment establish that these requirements work with the real model.

General assistant text is labeled discussion/interpretation and hypotheses, not code-verified facts. Quantitative result references carry only a checked candidate/projection identity, revision and supported metric name; code supplies the value, label, unit and basis. Unknowns stay unknown; invented savings/effect metrics cannot enter the checked result panel. Source observations, user/illustrative assumptions, calculated scenarios and qualitative proposals have distinct labels. This is a provenance boundary, not a semantic truth checker for unrestricted prose: real-model acceptance still fails any unsupported factual or numerical assertion, even when it is outside the checked result panel.

## Headcount scenarios

Projection is a model-directed tool, not a keyword branch. A fresh server loader reads the existing `dashboard_overview_filtered` contract and verifies its scope receipt. For all-company scenarios it also reads the existing current overview, configured scenario defaults and stored Baseline curve, requiring opening count/date agreement. No database schema or access policy changes are needed.

`configured_scenario` reuses `runScenarioModel` for company-wide assumptions. Its implied hires/exits are calculated by that engine. The stored scenario's hires/exits do not reconcile its reference curve and are not used as flow inputs. The stored Baseline must cover a complete forward window from the active opening snapshot.

`monthly_flow` calculates opening + external hires − exits + scoped transfers in − scoped transfers out. Monthly hires/exits must be explicitly supplied as user or visibly illustrative assumptions. Unspecified transfers are an explicit zero-transfer assumption. Internal transfers cannot add company-wide headcount. Filtered populations cannot borrow company-wide scenario defaults. Infeasible negative counts are rejected, not clamped. Hiring cohort percentages are not converted into headcount flows.

Charts include opening count, source date/scope, assumptions, monthly values, method limits and an input-content digest. The active-v1 sources expose no dataset version/token, which is explicitly reported as unavailable; the digest is not a dataset-version attestation. Follow-ups such as slower hiring reference an exact previous analysis revision, then use freshly read source inputs. A changed input digest is disclosed.

The source loader is a separate server adapter. A future activated dataset router must validate its token, cutoff, scope, digest and contiguous receipts before mapping into these calculation inputs; it must not mix versions or invent future observations. This implementation neither imports nor activates the September candidate, and never substitutes its local 9,847 baseline. It does not wait for dataset cutover. These are assumption-based scenarios, not independently validated predictions or trained forecasts.

## Validation and preview gates

Fixed provider-output fixtures test software contracts, not real-model understanding or usefulness. The new tests cover open discussion without saved plans, descriptive blends and activity replacement, same people, relative quantities, corrected constraints, feedback/recovery, clock-to-deadline conversation, projections, stale/cancel/save behavior and malformed state. Browser tests intercept all model/evidence responses; there are no paid calls.

The default-disabled build retains the existing flow. Enabling the new feature requires an explicitly approved branch-specific preview build/runtime flag and a new preview deployment, with production left disabled. No hosted settings are changed automatically. A local fixture test is not a publicly accessible or real-model-enabled preview.

Real-model acceptance must use this final contract and multi-turn scenarios; the older twelve-call protocol plan must not run. Proposed evaluation: six three-turn scenarios (18 user turns), at most four provider requests per turn (72 total), no retries or paid web integration. Use controlled evidence/saved-plan fixtures with the actual configured model, record raw responses/tool arguments/results and usage privately, and score both substantive conversational usefulness and semantic correctness against the user's intent. Any invented clock/data, wrong reference/unit, lost correction, hidden assumption, false Save claim or unsafe stale save fails acceptance. Do not infer language quality from deterministic fixture passes.

Scenario families: ordinary time → discussion → deadline review; “I want to reduce turnover” → creative proposals before pinning → local intentional selection automatically pins/attaches → conversation refinement → correction (three paid conversation turns; the local selection is not a model call); descriptive blend → component replacement → keep mentoring; same people → halve that → corrected constraint; calculator rejection → refinement → explanation; headcount projection → slower hiring → source/scope limitation. Local browser checks separately cover cancellation and persistence without wasting paid calls. Costs and a concrete execution ceiling require approval before the first model request. Preview enablement and model-evaluation authorization are separate from merging or production deployment.

For the proposed 18-turn evaluation only, reserve a **US$4.50 ceiling**, with no automatic reruns. The prepared offline reservation guard is `tests/helpers/solution-evaluation-budget.mjs`; it does not make requests or authorize execution. Limits are 18 turns, four provider rounds per turn, 72 provider requests total, one in flight, and at most six request starts per rolling minute. Each request must have a locally verified full-request input-token upper bound no greater than 200,000 and `max_output_tokens=5000` (including reasoning/output tokens). The service's 120,000 UTF-8 input-byte cap remains in addition to token verification. No remote token-count, web, paid tool, retry or model-switch calls are included.

Reserve the full 200,000 input and 5,000 output tokens durably **before** every request, including requests that later fail, time out or are cancelled; never refund reservations to authorize extra calls. At $0.25/M input (the $0.20/M standard rate with the 1.25× cache-write premium) and $1.20/M output, this reserves $0.056 per request, **14.4 million input + 360,000 output tokens and $4.032 total**, leaving $0.468 inside the proposed ceiling. Use no discounted-cache assumption and stay below the >272K long-context threshold. Stop before the first request unless the configured endpoint/standard-tier rates and a correct local full-request token bound are verified. Those execution preflights remain pending; a byte count alone is not a verified provider token count. Any taxes or endpoint surcharges must fit the remaining reserve or the batch must shrink before execution; no billing changes.

**Hosted acceptance calls included: zero.** The 18-turn evaluation uses controlled local context with the real configured model. Hosted preview enablement, any hosted acceptance calls, and the user's later manual preview testing are separate scopes. The proposal does not grant unlimited manual spend or enable a paid public endpoint. A hosted or manual allowance must be bounded and explicitly approved before it is enabled. The guard rejects hosted requests. No model calls or paid token-count calls have been made for this slice.
