# Expected outcomes: minimum data-readiness proposal

**Decision requested for a later phase:** review six logical record contracts below, then qualify one population/metric per domain. This artifact proposes fields and acceptance tests only. It implements no schema, data capture, forecast, effect model, access change or product integration. No new database query was used: evidence comes from existing audits and repository contracts. All supplied observation history must retain its actual provenance.

## What an expected outcome means

| Output | Required meaning | Current permitted interpretation |
| --- | --- | --- |
| Baseline forecast | Future outcome under a specified continuation of conditions, population, metric and horizon. | Turnover has a conditional retrospective synthetic count demo. Hiring has tested constructed-fixture fitting. Satisfaction forecasting is unqualified. A historical trend alone does not establish a no-intervention counterfactual. |
| Scenario calculation | Outcome conditional on explicitly supplied baseline, effect size, timing and cost assumptions. | Existing retention what-if arithmetic uses user assumptions. It must retain that label; missing effects remain unknown. |
| Estimated intervention effect | Contrast between specified intervention and comparison conditions for the same target population and outcome horizon, supported by an identification design. | Unavailable for all three domains. Goal intent, historical associations and generated benefit assumptions do not supply this evidence. |

A later goal result should retain `population_definition_version`, `metric_definition_version`, `unit`, `forecast_origin`, `outcome_window`, `baseline_assumptions`, `evidence_kind`, `data_as_of`, `limitations`, and unavailable-or-estimated uncertainty with its method/validation basis. Attach intervention identity and effect design only when those exist. Do not sum overlapping interventions, interpret predictive feature importance as intervention efficacy, or turn an uncalibrated range into confidence. A missing forecast or effect is null with a reason, not zero.

Keep the user-authored `goal_target_value` and `desired_direction` separate from observations and estimates. A point forecast can support a clearly labeled gap-to-goal calculation only for the same metric/population/horizon; it does not establish the probability of achieving the goal. That probability stays unavailable without an appropriate calibrated predictive distribution.

## Six proposed logical contracts, no migration

Names describe record shapes. Reuse/extend existing source metadata where available; a new physical table is needed only if the source cannot retain these records. Internal reconciliation keys stay within the current source boundary; these contracts authorize no new extraction or service payload.

1. **Shared `history_provenance`** — an extract manifest plus version metadata attached to each domain record. Manifest: `extract_id`, `source_id`, `source_definition_version`, `population_definition_version`, `metric_definition_version`, `data_class`, `generator_version` (required for newly constructed demos), `extracted_at`, and `complete_through` with population/period scope, evidence and `complete|partial|unknown` status. Version envelope: stable internal `record_key`, `revision_id`, `supersedes_revision_id`, `effective_at` or effective period, independently evidenced `source_first_observed_at`, `ingested_at`, and correction reason. Unknown first-observed time stays null. Append corrections; preserve prior values so a query at time T uses only revisions observed by T. Ingestion and event dates are separate facts. Backfilled records do not retroactively become available. A completion watermark requires reconciliation/closure evidence; elapsed calendar time or the largest event date is insufficient.

2. **`turnover_period_history`** — `(population_version, period_start, period_end, revision_id)`; `voluntary_exit_count`, `classification_definition`, `count_status`, and shared metadata. Optional for rates: `exposure_value`, `exposure_unit`, `exposure_definition_version`, `exposure_status` and eligibility/scope alignment. Missing, suppressed and incomplete counts are null; confirmed zero requires source completeness evidence. Distinguish a proportion using agreed headcount from an incidence rate using person-time, and match units/periods. Forecast future exposure independently or label an explicit scenario denominator. Source keys for deduplication are internal, not model features.

3. **`satisfaction_wave_history`** — `(wave_id, population_version, metric_definition_version, revision_id)`; `instrument_version`, `item_set_version`, scale/range, reverse/excluded-item rules, weights, minimum answered items, favorable/neutral/unfavorable thresholds if defined; `launch_at`, `close_at`, `finalized_at`, `eligible_population`, `valid_respondents`, `denominator_snapshot_date`, `response_unit`, `metric_value`, `coverage_status`, `suppression_status` and shared metadata. For mean respondent favorable answer share, retain its definition and aggregate sum of valid respondent shares plus count when authorized; do not relabel as an integer count of favorable people. Any uncertainty sufficient statistics must match that estimand. Eligible population is not the favorable-share denominator. Wave-to-wave item/population changes require a justified bridge or a break in the series; no monthly interpolation of annual waves. Begin company-wide with the existing approved metric. Existing minimum-group, complementary-suppression and cross-query controls remain required for any later subgroup release; new subgroup access is outside this proposal.

4. **`hiring_event_history`** — version the existing event records rather than create parallel final-state copies. Internal requisition/offer/start keys; chosen role and scope as known at opening; event kind, effective time, independently observed time and revision envelope for approval, opening, offer acceptance/decline, planned-start changes, recorded actual start, cancellation, no-show and closure. Retain unresolved cases and reason for unknown status. Define `hire_date` explicitly: observed equality with offer acceptance in all 5,080 audited hires is not a universal definition. Recorded actual start is distinct from planned start even though they coincide in this extract. No productive-capacity timestamp is inferred. Calendar-only fitting needs no post-opening pipeline counts or employee attributes.

5. **`intervention_study`** — `study_id`, version, goal/target metric and population versions, intervention/comparator definitions, assignment unit, planned/actual assignment dates, assignment mechanism and reasons, rollout dates, intended lag/duration, outcome horizon, pre-specified analysis/eligibility/exclusion rules and observation envelope. Record a reproducible random assignment protocol when feasible; for observational rollout, state the identification strategy, relevant pre-assignment confounders, overlap and sensitivity requirements. Store where design assumptions may fail, including concurrent programs and spillovers. Do not treat a design description or trend test as proof that those assumptions hold. Allocation must precede outcomes used to evaluate it.

6. **`intervention_group_period`** — `(study_id, assignment_group, period, metric_version, revision_id)`; intended assignment, actual exposure start/end, dose/adherence, eligible/assigned/exposed counts, aligned pre/post outcome totals or sufficient statistics and denominators for intervention and comparison groups; attrition/nonresponse, contamination/concurrent changes and shared metadata. Preserve assignment for an intention-to-treat contrast even with nonadherence; any exposure-based contrast needs its own assumptions. Use matched time windows and metric versions. Turnover counts need exposure reconciliation; satisfaction needs comparable response coverage/scoring; hiring needs comparable role/opening cohorts and censoring accounting. No public person-level study rows are proposed. Dates alone cannot identify an effect; analysis must support the counterfactual and account for assignment unit, clustering and repeated measures.

## Small synthetic-demo plan and acceptance gates

Start with constructed files in an isolated test area, never enrich existing company records with invented historical timestamps. Label every generated record `constructed-synthetic`, pin seed/generator/protocol/code versions and explicitly separate simulated `event_at`, simulated `observed_at`, simulated revisions and actual file generation time. Simulated time is a property of the fictional process, never evidence of source-system history. Keep ground-truth effects in a generator-only sidecar unavailable to fitting/selection.

Use one population and one outcome definition per demo. Generate stochastic counts with nonnegative exposure; delayed/revised exit reports and true zeros. Generate satisfaction only at actual simulated waves with bounded item scores, item nonresponse, changing response propensities, instrument breaks and suppression cases. Generate all requisition openings before outcomes, ordered stages, unresolved/cancelled searches, variable accepted-to-start lags, and planned-versus-actual start deviations. Do not force perfect uptake, plan accuracy, universal benefit or exact forecast fit. Productive capacity stays unknown unless separately simulated and labeled.

For effects, generate a small cluster-assigned comparison study with multiple independent units per arm and pre/post periods, plus a deliberately confounded/nonrandom comparison case. Include zero, adverse, delayed and heterogeneous effects, nonadherence and spillovers. Generate the treatment mechanism and outcomes first; never generate candidate predictions by adding chosen errors to labels. Ground-truth recovery on invented cases tests mechanics only, not real efficacy or source readiness. Do not tune until a desired positive result appears.

Freeze temporal folds, preprocessing, recency choices and selection rules before revealing the final generated assessment. Where event/wave history permits, compare 12/24/all history on aligned cases; use wave counts for satisfaction and report when such calendar windows contain too few comparable waves. There is no universal year-count gate: report eligible events/waves/independent groups, exclusions and maturity at each origin. The previously inspected company extracts cannot become untouched holdouts. Retain a simple baseline when the fitted model fails the fixed criterion; retain null effect/uncertainty when design or calibration is insufficient. Prediction intervals and causal-effect uncertainty are different outputs and require their own checks.

[Machine-readable acceptance cases](../tests/contracts/predictive-readiness.proposed.json) specify failure and boundary tests. They are **proposed test vectors, not an implemented validator or passed behavioral suite**. Structural JSON/reference checks can run now; source capture, model fitting and causal validation remain later work.

**Exact next slice proposed:** agree the shared metadata semantics; choose one company-wide turnover count, one existing satisfaction scoring definition/wave series, and one hiring role; reconcile available history against contracts 1–4. Independently design one intervention/comparison study using 5–6 before claiming goal-based effects. Defer richer pay/manager/training covariates, cross-domain joining, productive-capacity modeling and additional filters until a baseline and the source history justify them. This is a review proposal, not approval to execute any of those steps.
