## Reproduce the invented second company

From the repository root with Node 24.21.0 (the tested version):

```powershell
node tools/import-company-fixture.mjs tests/fixtures/company-import/lantern-config.json tests/fixtures/company-import/lantern-rows.json
node --test tests/company-fixture-import.test.mjs tests/public-fixture-provider.test.mjs
```

The CLI prints `{manifestText, manifestSha256, report}` to stdout. It writes no file or runtime state. `manifestText` can be passed directly to `createPublicFixtureProvider(manifestText, manifestSha256)` for local tests. That newly computed digest describes these generated bytes; it is **not an independently trusted approval pin**. Review and pin artifacts separately before any later integration. CLI errors return exit 1 with a fixed message and no source payload/path. The library returns categorized errors without row values.

Lantern is entirely invented for this test. Its two leaf divisions have 7 people / 6 FTE in August and 9 people / 7.75 FTE in September 2026. These values do not reproduce production. The four input rows are deliberately out of order. Output orders snapshots by the strictly ordered control list, and latest headcount is 9. Existing fixture provider tests retain their distinct 10-to-12 example.

## Review the mapping before importing

The fixture's assumed source owner is the fictional Lantern Workforce Reporting team. The sample declares active people counted once in exactly one nonoverlapping leaf division at each month end. Contractors, overlapping parent totals, person records, pay, leave rules and history corrections are outside this example. A real owner must define those population rules before a private ingestion implementation; a config declaration cannot prove them.

| Destination | Lantern source | Transformation and unit | Validation |
| --- | --- | --- | --- |
| `snapshot_date` | `period_end` | Exact ISO calendar date, month-end in this example; no date guessing | Actual date and membership in reviewed controls |
| `org_code` | `division_key` | `workshop` to `OPS`; `studio` to `DESIGN` | Explicit one-to-one leaf crosswalk; no inference from names |
| `headcount` | `staffed_people` | Distinct-person snapshot count, unchanged | Nonnegative safe integer; strings/null rejected |
| `fte` | `capacity_percent_total` | Sum of contracted FTE percentages divided by 100; 325 means 3.25 FTE | Nonnegative integer percent sum, FTE at most headcount |

Alternatively `fteUnit: "fte"` accepts numeric FTE to hundredths, with a small tolerance for binary floating point representation. No rounding of finer source precision, allocation weighting, annualization, percentage-of-headcount inference or arbitrary expressions is supported. A percentage **rate** is not a percent **sum**. Choose the unit explicitly and reconcile it with the owner.

All config/row objects have closed key sets. Source field names must be distinct. Every configured unit/date pair must have exactly one row, including explicit zero populations. Missing, null, empty, string-numeric and unknown fields fail; nothing is silently zeroed, filtered, suppressed or merged. Config controls hold independently reviewed company headcount/FTE totals for each date. Do not derive controls from the same export and claim independent reconciliation. Aggregates must match these totals exactly in integer hundredths of FTE; overflow fails. Limits: 1 MiB per JSON text, 100 leaf units, 120 snapshots (12,000 rows maximum). Totals reconcile counts; they cannot establish that the source really deduplicated people or excluded hierarchy overlap.

Only headcount and trend bodies enter the manifest; company labels, crosswalk/source values and the report remain outside it. The report records exact source/config SHA-256 digests, field mapping, declared FTE unit and coverage counts. Retain the reviewed config beside it to recover the crosswalk and controls. These audit records do not establish publication approval. Only invented fixture inputs are authorized in this lane; do not feed real workforce exports to this CLI or publish their artifacts. Extra-column rejection is schema enforcement, not a privacy classifier.
