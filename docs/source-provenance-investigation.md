# Source provenance investigation and minimal augmentation proposal

Investigation date: 2026-10-05. Inspected checkpoint: `8d452186b69867cf40872f687eb8d25da567f973`. This is a read-only repository investigation with a local design proposal. No source query, SQL execution, schema/access change, generator replacement or UI change was made.

**Result:** available artifacts establish the implementation of several separate demonstration generators and some source calculation semantics. They do not establish the generator, complete event universe or as-known label vintages of the loaded workforce dataset. None of the three operational forecast eligibility decisions changes. Finding a seed alone would not recover historical availability.

These identify inspected files; they are not source authenticity attestations. Earlier database observations are reused from their saved reports, not freshly reverified. ## Smallest concrete proposal: three local export sidecars

Start with reviewable files beside an authorized export. These are logical field contracts, **not** proposed new database tables, executed SQL or a request for broader access. The [sample rows](evidence/provenance-augmentation.examples.json) are expressly invented examples, not repaired source history. Generator output hashes are null where no executable generator produced the examples, so they cannot pass a reproducibility claim.

1. **`run_manifest`**, one per actual export/generator run: `run_id`, `data_class` (`user-declared-synthetic` / `constructed-synthetic` / independently established source class), `generator_artifact_ref`, `generator_sha256`, `generator_version`, `seed`, `config_sha256`, `runtime_version`, `generated_at`, `exported_at`, `output_sha256`, `source_definition_version`, `population_definition_version`, `metric_definition_version`, and `temporal_basis` (`source-observed`, `simulated`, `unknown`). A reproducible recipe must include dependencies, source input/config hashes, deterministic ordering, timezone, generator options and expected scope. A human-entered version string is not enough. Existing unknown fields stay null.
2. **`coverage_declaration`**, one per domain/scope/window/revision: `coverage_id`, `run_id`, `domain`, `scope_key`, `window_start`, `window_end`, `status` (`complete`, `partial`, `unknown`), `expected_units`, `exported_units`, `coverage_unit`, `evidence_ref`, `source_attested_at`, `simulated_attested_at`, `revision`, `supersedes`. Expected units must come from the generator's complete enumeration or an independently reconciled source ledger, not a count of the same exported rows. Matching totals alone cannot detect omission plus duplication. Unknown expectation/coverage remains unknown. Completion covers capture of the defined window, not maturity of every unresolved hire or a guarantee that no future correction will arrive.
3. **`aggregate_revision`**, one per stable aggregate key/version: `run_id`, `domain`, `record_key`, `scope_key`, `metric_definition_version`, `revision`, `supersedes`, `effective_at`, `source_first_observed_at`, `simulated_first_observed_at`, `captured_at`, `availability_evidence_ref`, `status` and domain payload below. Preserve all revisions. `effective_at` is the period/wave/event time represented; `captured_at` is when this file actually captured it. Neither supplies missing first-observed evidence. Never write a simulated timestamp into the source-observed column. Same key/revision must have immutable content.

The simulation columns allow an honest *new* constructed demonstration when historical knowledge cannot be recovered. Select them only under an explicit constructed-data mode. Existing bulk-loaded records with unknown availability remain ineligible for source replay. If the original generator is recovered and its exact artifact/config/output can be matched, that establishes synthetic generation lineage and intended generated-universe coverage, not real observations or historical system availability. A new reporting-delay model would be an additional simulation assumption, never a recovered historical fact.

Domain payloads:

- **Turnover:** `month`, `voluntary_exits` (nonnegative integer or null), `count_status`, `classification_version`. A verified empty period may be zero. Optional rate work later requires matched population/person-time and exposure definition/revision; month-end stock is insufficient.
- **Hiring:** `role_scope`, `opening_cohort`, `as_of`, `followup_definition`, `status_bucket`, `count`, `opening_to_acceptance_days`, `opening_to_actual_start_days`, `capacity_ready_days`. Each row is an aggregate bucket of cases with the same target duration/status. Unresolved/cancelled cases retain null duration; every opening is reconciled once in mutually exclusive disposition buckets at each cutoff. Pair stages internally using existing keys; do not infer stage pairing from aggregate marginal totals. Censoring age/buckets and no-show disposition need explicit preservation for any all-openings estimator. This proposal alone is not an adapter to the existing requisition-level hiring experiment.
- **Satisfaction:** `wave_key`, `launch_at`, `close_at`, `instrument_version`, `item_set_version`, `scoring_version`, `eligibility_version`, `unit`, `favorable_share_sum`, `valid_respondents`, `eligible_count`, `missing_or_invalid_respondents`, `metric`, `release_status`, `release_review_ref`. Mean favorable-answer share is `100 * share_sum / valid_respondents`, not item-pooled share or percent satisfied employees. Participation uses the eligible count. All sensitive counts/sums/metrics capable of reconstructing a withheld cell must also be withheld. Release review must cover complementary totals and overlapping queries, not only a cell-size minimum.

## Validation checks before any evidence upgrade

1. Reproduce the original generator in an isolated local export only if the actual code/config/dependencies are supplied. Compare exact output hashes and scoped counts with the audited export; investigate differences rather than changing the seed until it matches. The example sidecar's null generator/config/output hashes must fail this gate.
2. Reconcile scope-specific units against a separately enumerated expected universe, uniqueness and relational pairing. Count equality alone is insufficient. Distinguish snapshot people, exit events, openings and survey invitees/respondents; none is interchangeable.
3. Check revision uniqueness/ancestry, immutable same-version content, canonical timestamps and evidence references. Keep source-observed and simulation timestamps mutually exclusive. At each origin include only versions and completion attestations actually available by that cutoff. If source records legitimately contain plans before future effective dates, retain the planned-event status and do not treat them as observed outcome labels.
4. Turnover: retain every calendar month, count true zeros only with coverage evidence; reconcile voluntary reclassification deltas and population. Confirm rate denominator separately.
5. Hiring: sum disposition counts to all openings, retain unresolved and cancelled cases, distinguish acceptance/actual-start/capacity, and report maturity/censoring at the scoring cutoff. Later completion cannot overwrite the old training vintage. Test a late start/cancellation and a plan revision.
6. Satisfaction: validate each versioned scoring rule, distinguish respondent-share and participation denominators, retain nonresponse/invalid cases, enforce approved release/query set, block instrument/population breaks without a justified bridge. Null/suppressed is never zero; unfavorable is never inferred as `100 − favorable`.
7. Keep historical source readiness, synthetic reproducibility, retrospective benchmark performance and causal identification as separate outcomes. A complete generator run can validate the constructed universe; it cannot certify real-world prediction quality or effect size.

The smallest immediate handoff is the **original generator bundle and its run/config/output manifest**, if retained by the dataset author, plus the scoring/field-definition documents. If unavailable, the honest options are a newly versioned constructed demo or future observation capture through a separately reviewed process. This investigation does not authorize either source mutation or retrospective fabrication.
