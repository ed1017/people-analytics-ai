## Smallest supported engineering step

Add a **pure local export-custody helper** beside the existing aggregate exporter, with no API calls, UI integration or model changes. Given an already authorized aggregate payload/export, it would retain the exact file hash, source/metric/scope identifiers, each record's effective period and the actual packaging time. Attach a sidecar that keeps source-first-availability, source revisions and completion explicitly null/unknown unless supplied by supported evidence. Distinguish a local capture sequence from a source revision. A capture made now must never be backdated or treated as proof of historical source availability.

Use the captured monthly count fixture as a non-sensitive compatibility example; retain its extraction date precision, declared-synthetic provenance, 32 event-bearing months and unknown January count. For future CSV bundles, retain both the record period and top-level `as_of`; do not assign the latest snapshot date to every historical row. Mark routes with null-to-zero coercion as unsuitable for recovering original missingness rather than guessing which zeros were missing. Reuse `validatePredictiveReadiness` and the existing checkpoint's unavailable outcome, instead of building another model or a second readiness engine.

This is the smallest independent code increment supported by the existing payloads. It would improve reproducibility and make gaps machine-readable, but **would not qualify historical forecasting**. Original null/status values, scoped completeness and independently evidenced availability still require authorized source evidence. If old vintages cannot be recovered, future authorized captures can accumulate a prospective series; capture automation or new access is not implemented or authorized by this inventory. The helper itself is proposed here, not implemented.
